# Coordination Artifact Schema

Ground truth for this doc is the shipped validator (`.claude/hooks/coordination-artifact.js`, `validate(kind, filePath, ctx)` / `hasValidConsult(dir, ctx)`) and writer (`scripts/sh/write-coordination-artifact.sh`). Field tables below mirror exactly what each checks/writes.

## Storage & Naming

| Schema | Path | Directory or flat file |
|--------|------|------------------------|
| `coordination/consult/v1` | `inbox/context-provider/consult-<ts>.json` | directory (bounded scan for newest valid) |
| `coordination/message/v1` | `inbox/<to>/<from>-<ts>.json` (+ `outbox/<from>/` mirror, identical content, not independently validated) | directory |
| `coordination/result/v1` | `results/<from>/<from>-<ts>.json` | directory |
| `coordination/request/v1` | `requests/<kind>/<from>-<ts>.json` (`<kind>` = the request's own top-level `kind` field, e.g. `scope-extension`; filename stem = `request_id`) | directory |
| `coordination/approval/v1` | `approvals/<request_id>.json` (`<request_id>` = the request being resolved, supplied via `--re`) | flat (no role/kind subdir) |
| `coordination/stop/v1` | `stop-<to>.flag` (`<to>` = the role being told to stop) | flat sentinel file |

- `<ts>` = compact UTC timestamp, `date -u +%Y%m%dT%H%M%SZ` (colon-free — Windows-safe). `created_at` inside the body is full ISO-8601 (`%Y-%m-%dT%H:%M:%SZ`), a separate value from the filename timestamp.
- `<from>` / `<to>` = canonical agent names (`subagent_type`). The writer requires both non-empty and path-safe for EVERY kind, before kind-specific branching — but the validator only checks them as part of the shared base envelope (message/result/request/approval); for `consult` only `to` is checked (must equal `context-provider`); for `stop` neither is checked (presence-only).
- `request_id`: for a `request/v1`, auto-generated by the writer as `<from>-<ts>` (never caller-chosen); for `approval/v1`, supplied via `--re <request_id>` and MUST name an existing, currently-valid request.
- Directories are created on first write (`mkdir -p`, confined under `.planning/wave-<slug>/`); readers MUST NOT assume they pre-exist.

## Bounded-Scan Confinement (HARD)

Every read is confined to one named, non-recursive directory or one named file — never a glob across `.planning/wave-*/` or across roles:

- **Approval → request** (not the reverse): an `approval/v1` names exactly one request via `request_kind` + `request_id`; the validator resolves `requests/<request_kind>/<request_id>.json` (realpath-confined, sanitized against traversal) and requires that file to exist AND itself pass `request/v1` validation — an approval pointing at a missing or now-stale request is invalid (forge/replay guard).
- **Consult** — `hasValidConsult(dir, ctx)` performs a bounded, non-recursive scan of exactly `inbox/context-provider/` for files matching `consult-*.json`: aborts closed if more than 1024 entries are seen (`MAX_CONSULT_HARD_CAP`), keeps at most the newest 256 candidates (`MAX_CONSULT_ENTRIES`), skips (never reads) any file over 64KB (`MAX_CONSULT_BYTES`), and checks newest-first until one validates. A caller that already has an exact path instead calls `validate('consult', filePath, ctx)` directly — no scan.
- **Message** — a reader scans only its OWN `inbox/<to>/` subdirectory; the `outbox/<from>/` copy is a sender-side courtesy mirror, not a second artifact to validate.

## ArtifactValidation Contract

Every kind is read through the same 4-field contract from [ADR-001 §3.2](../adr/ADR-001-runtime-adapter-contract.md): `exists`, `validMarker`, `headBound`, `fresh`. The 3 validation models the code actually implements:

| Field | `consult` | `message` / `result` / `request` / `approval` | `stop` |
|-------|-----------|------------------------------------------------|--------|
| `exists` | file present at the exact path | file present at the exact path | file present, basename matches `stop-<safe-segment>.flag`, direct child of the wave dir |
| `validMarker` | `schema === "coordination/consult/v1"` AND `to === "context-provider"` | `schema === "coordination/<kind>/v1"` exact string, plus the kind-specific rule (see per-schema tables below) | **optional** — empty file or non-JSON body is valid (presence IS the signal); if a JSON body is present, `schema`/`wave_slug` are checked only when those keys exist at all |
| `headBound` | not applicable — no `head` field | `head` is a 40-hex string AND an ancestor of (or equal to) current HEAD (`git merge-base --is-ancestor`) | not applicable — no `head` field, even when a full envelope is optionally written |
| `fresh` | `wave_slug` matches AND `created_at` ∈ `[now - CONSULT_TTL_SECONDS, now + MAX_CONSULT_FUTURE_SKEW_SECONDS]` (12h past / 5min future-skew — directional, not symmetric) | `wave_slug` matches AND `plan_sha256` exactly equals the current `PLAN.md` sha256 | no freshness check — `wave_slug`, if present in an optional JSON body, is checked for equality but absence is not a failure |

**Why consult is TTL-only, not HEAD/PLAN-bound**: a CP consult answers a pattern/precedent question — it isn't authorizing a write against specific PLAN content the way a dispatch or verdict is. Binding it to HEAD ancestry would force a fresh consult on every commit, defeating the portable gate's purpose. **No `session_id` field on any schema** — a portable shell has none to source; the table above is the entire currency check per kind.

## The 6 Schemas

### `coordination/consult/v1`

The disk-fallback branch of the CP-consult gate — see [context-provider-adoption-hooks § Hook 1](context-provider-adoption-hooks.md#hook-1-context-provider-gate). `to` MUST be `context-provider` (the only valid recipient for this kind — enforced by both the writer and the validator).

| Field | Type | Validated? | Description |
|-------|------|------------|--------------|
| `schema` | string | yes — exact `"coordination/consult/v1"` | the `validMarker` |
| `wave_slug` | string | yes — must equal active wave | active wave directory slug |
| `to` | string | yes — must equal `"context-provider"` | fixed recipient |
| `from` | string | written, not validated | canonical name of the consulting agent |
| `created_at` | string | yes — directional TTL (12h past / 5min future-skew, not symmetric) | UTC ISO-8601, `date -u +%Y-%m-%dT%H:%M:%SZ` |

No `head` / `plan_sha256` — consult is pre-PLAN by design.

### `coordination/message/v1`

Op 2 (`send`) disk-inbox fallback. No kind-specific field beyond the base envelope — "base fields are the whole contract."

| Field | Type | Validated? | Description |
|-------|------|------------|--------------|
| `schema` | string | yes — exact `"coordination/message/v1"` | |
| `wave_slug` | string | yes | active wave directory slug |
| `from` | string | yes, non-empty | sender's canonical name |
| `to` | string | yes, non-empty | recipient's canonical name (path directory) |
| `created_at` | string | yes, parseable | UTC timestamp |
| `plan_sha256` | string | yes, exact match | sha256 of the wave's `PLAN.md` |
| `head` | string | yes, 40-hex + ancestor-of-HEAD | `git rev-parse HEAD` at write time |

### `coordination/result/v1`

Op 4 (`result`) disk-artifact fallback.

| Field | Type | Validated? | Description |
|-------|------|------------|--------------|
| `schema`, `wave_slug`, `from`, `to`, `created_at`, `plan_sha256`, `head` | — | yes (base envelope) | same rules as `message/v1` |
| `status` | string | yes — must be `ready-for-review` \| `done` \| `blocked` | completion state |
| `re_dispatch`, `files_touched[]`, `summary`, `detail` | — | **not gate-validated** | informational body fields (writer/PLAN convention, not checked by `validate()`) |

### `coordination/request/v1`

Scope-extension / authorization requests — the portable-mode equivalent of the `SendMessage` template in [scope-extension-protocol § How to Request Authorization](scope-extension-protocol.md#how-to-request-authorization).

| Field | Type | Validated? | Description |
|-------|------|------------|--------------|
| `schema`, `wave_slug`, `from`, `to`, `created_at`, `plan_sha256`, `head` | — | yes (base envelope) | same rules as `message/v1` |
| `request_id` | string | yes, non-empty | auto-set by the writer to `<from>-<ts>`; names the resolving `approval/v1` |
| `kind` | string | required by the writer (e.g. `scope-extension`); read by the validator to branch the `files[]` rule | routes the `requests/<kind>/` subdirectory |
| `files` | array (top-level, NOT nested in a body block) | yes when `kind === "scope-extension"` — must be non-empty | repo-relative paths this request concerns |
| `blocker`, `root_cause`, `proposed_fix`, `why_not_defer` | — | **not gate-validated** | informational body block mirroring the SendMessage template — the validator only checks `request_id`/`kind`/`files` |

### `coordination/approval/v1`

The orchestrator's resolution of exactly one `request/v1`, matched by `request_kind` + `request_id` — never a glob over `approvals/`.

| Field | Type | Validated? | Description |
|-------|------|------------|--------------|
| `schema`, `wave_slug`, `from`, `to`, `created_at`, `plan_sha256`, `head` | — | yes (base envelope) | same rules as `message/v1` |
| `decision` | string | yes — must be lowercase `authorized` \| `denied` | resolution |
| `request_id` | string | yes — safe path segment | must reference the linked request's own `request_id` |
| `request_kind` | string | yes — safe path segment, required | the linked request's `kind` — resolves `requests/<request_kind>/<request_id>.json`, which must exist AND itself validate |
| `approver` | string | written (defaults to `from` if the body omits it), not independently checked | who authorized/denied |

### `coordination/stop/v1`

Op 5 (`stop`) disk-artifact fallback — graceful-shutdown sentinel. Content is genuinely OPTIONAL: the writer produces a bare zero-byte file when invoked with no stdin body; the validator accepts an empty file, a non-JSON body, or a JSON body (in which case `schema`/`wave_slug` are checked only if those keys are present at all). No `from`/`created_at`/`head`/`plan_sha256` requirement, even when a caller supplies a fuller body.

| Field | Type | Validated? | Description |
|-------|------|------------|--------------|
| (none — bare file) | — | filename pattern + direct-child-of-wave-dir only | `stop-<to>.flag`, `<to>` = safe segment (the role being told to stop) |
| `schema` | string | only if the key is present at all | `"coordination/stop/v1"`, if supplied |
| `wave_slug` | string | only if the key is present at all | active wave slug, if supplied |

The agent checks for this file at checkpoint boundaries, per [ADR-001](../adr/ADR-001-runtime-adapter-contract.md) Op 5.

## Writer Contract

Two sanctioned write paths, mirroring [context-bundle-schema](context-bundle-schema.md)'s Writer Contract:

1. **`write-coordination-artifact.sh --kind {message|consult|request|approval|result|stop} --from <role> --to <role> [--file <path> ...] [--re <request_id>] [--slug <wave-slug>]`** (portable script, invoked via Bash), kind-specific body as an optional JSON object on stdin. Slug resolution, in order: `--slug` flag → `CLAUDE_WAVE_SLUG` env → git branch last-segment → a single `.planning/wave-*/PLAN.md` alias. The script authors `created_at`/`head`/`plan_sha256` (where applicable) and writes ONLY under the schema's canonical subdirectory, confined under `.planning/wave-<slug>/`.
2. **Direct write** — any file-capable engine (not only Claude) may write these artifacts directly via its native file-write primitive; the schema, not the orchestrator or a particular script, is the contract. Same portability posture as [ADR-001](../adr/ADR-001-runtime-adapter-contract.md) §4.4's Future Engine Adapter baseline.

## CP-Consult Unblock

`context-provider-gate.js` gains a **disk branch**: when no live-SendMessage session flag exists, it calls `hasValidConsult(inboxDir, ctx)` (exported by `.claude/hooks/coordination-artifact.js`) — the bounded scan described above — before blocking. This lets a portable/single-use runtime — with no persistent peer to `SendMessage` — satisfy the same gate a live peer satisfies by messaging context-provider. `context-provider-consulted.js` (the existing SendMessage-side flag writer) is unchanged: a `PostToolUse`-on-`Write` writer for context-provider would be non-portable and would violate `CONTEXT_PROVIDER_READ_ONLY` (CP's Write/Edit/Agent tools stay banned); the gate-side disk READ is engine-agnostic and needs no new writer hook on CP's side. Full gate description: [context-provider-adoption-hooks § Hook 1](context-provider-adoption-hooks.md#hook-1-context-provider-gate).
